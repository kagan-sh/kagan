# kagan decisions

Checked 2026-10-05 against `main`. Terms follow [CONTEXT.md](CONTEXT.md). The shapes these decisions describe are in [architecture.md](architecture.md), [plugin-api.md](plugin-api.md), [self-extend.md](self-extend.md) and [look.md](look.md); this file is the record of what was chosen and why, so a later reader does not reopen a settled question. It does not state the current rule: the code and its tests do, and [AGENTS.md](../AGENTS.md) holds the rules for writing code. An entry that a later one replaces starts with "Superseded by N".

Each entry is the decision, the reason it won, and what it rules out. Where the code is the authority, the path is named.

## Product

**1. What kagan is.** A GPUI-based, self-extensible, agentic coding IDE for the people of a startup-sized company. Each person runs one host on their machine: agents, SQLite, the thread event log and plugins. The desktop window, `kg` and that person's phone are clients of their host, and speak the typed `Op` list as a versioned protocol with a pushed event stream. Teammates share plugins through the company's private marketplace (3), not a shared host. Today the host and the window are still one process, and `kg` is the only other client.
Why: a native app per person keeps the speed and the small bundle, and one owner per host keeps approvals honest (10). A team needs shared plugins and a phone before it needs a shared server.
Rules out: several people on one host, a hosted kagan server, public repositories and public tenancy before the private path works, and a client that reaches into `core` instead of going through `Op`.

**2. The plugin line.** A plugin adds panels, commands, agent tools, skills, CLI, settings, an overlay (100), and no other spots. Decision 56 refuses `thread-list` and `file-opener`. A plugin panel is placed `left`, `center`, or `right` (59); `bottom` is refused. Environment kinds stay the closed `Provider` set in `crates/core/src/environment.rs`: project, worktree, personal.
Why: the coding surface — threads, the terminal, diff, and worktrees — is what the tool is, and a plugin cannot be trusted with it. The voice part is superseded by 42. The in-app browser is removed (31).
Rules out: a plugin-supplied agent program or environment kind, and moving existing chrome out into plugins. Amended by 105: a plugin panel may replace the thread list body or the review body when the person picks it.

**3. What ships today, and the marketplace next.** Threads, the Rust surface, voice, diff, worktrees, and themes. Voice in this list is superseded by 42. The in-app browser in this list is removed (31). The company marketplace is a plugin index (103): a JSON list of plugins in a git repository or a folder. The host reads an ordered list of indexes, the company's private one first. Private repositories are reached with the person's own git or `gh` credentials. Install, update and approval stay as they are (14); the index only says where the code is.
Why: plugins already install from `git:<url>@<ref>` and are checked by commit, so an index is the only missing piece, and a private git repository needs no service to run.
Rules out, for now: a hosted catalog, ratings, signing, and a public index; a skill registry; an in-app browser; global hotkeys; and an answer `Op`.

**4. Ports stay notes.** The canvas, kanban, VSCodium and vocodr port studies were shaped-the-API examples for plugin authors, not a backlog.
Why: they did their job by finding the gaps in the plugin API. Hearing and speaking became the native voice path instead of a vocodr plugin. That native voice path is superseded by 42.
Rules out: a canvas or a board as a Rust panel beside diff and the thread list.

## Truth and recovery

**5. SQLite is the truth.** Thread rows and the append-only `events` table. GPUI entities are rebuilt when the process opens.
Why: a crash must not replay work or lose a turn, and only the database survives one.
Rules out: the live entity winning a disagreement, and rebuilding a thread row from events alone.

**6. What a restart recovers.** Archive and worktree-removal grace deadlines resume. Opening the app does not resume a program. Amended by 171: a thread left running is started again.
Why: the person's intent was recorded; a running program was not.
Rules out: resuming a program mid-turn, and replaying in-flight tool calls. Amended by 171: the program is started again, and its own conversation is what continues.

**7. There is no streaming-reply flush.** Nothing writes a partial reply on a timer. The log keeps the events that were stored.
Why: the person's program owns its own output in the terminal.
Rules out: a token flush, and a host-side streaming reply.

**8. A restart does not replay a transcript.** Nothing sends an old transcript back to a program.
Why: the event log is the record. A program starts only when the person runs it.
Rules out: seeding a program from the log, and a size limit on a transcript that is no longer sent.

**9. Copying a thread was removed as unused.** No window and no plugin called it. A copy of saved events does not continue a terminal program, and Start again already runs the same thread again.
Why: it left a thread that ran nothing.
Rules out: `kg thread fork` and `threads.fork`.

## Approvals

**10. Only a person approves.** Plugin powers resolve through `Workspace::answer` and `answer_standalone`. Those are not `Op`s; `crates/domain/src/tests.rs::answers_are_not_operations` keeps it that way. An `kg ui` click cannot answer. A plugin cannot answer a pending question. Answering removes the pending row and writes `answered`. Deleting the row is not an answer. Synthetic `kg ui` cannot answer. A phone answers by signing the pending request with a device key that lives in the phone's secure hardware and needs the person's face, fingerprint or passcode to use. The host keeps the paired device's public key and checks the signature before answering.
Why: if an agent can approve its own request, every other power is decoration. A key that needs the person present proves a person; a click on a socket does not.
Rules out: an answer `Op`, a plugin answering a pending question, approval from `kg`, a synthetic `kg ui` answer, a phone answer without a fresh signature, and a key the host or an agent can read.

**11. Agent programs are not installed here.** Kagan does not install or remove the program a thread runs. A thread runs the program the person names.
Why: installing an agent program is installing code. The npm path has no checksum to offer, so refusing an unverified package would refuse most of the registry.
Rules out: silent provider installs, and a hard checksum requirement before the registry carries one for every entry.

**12. Delete and plugin remove ask.** `ThreadOp::Delete` and `PluginOp::Remove` raise a pending interaction. Archive, unarchive, stop and send stay `Op`s an agent may run.
Why: archive is reversible within the grace; delete and remove are not.
Rules out: an agent deleting a thread or a plugin on its own, and `kg thread archive` waiting for a person.

**13. A question waits.** A pending interaction with no window open sits until the person answers it. It does not time out.
Why: a timeout that denies is a decision nobody made; a timeout that allows is worse.
Rules out: both defaults.

**14. A plugin is checked by its recorded git commit.** An update whose powers grew asks again. A `downloads` key or `powers.spawn` is refused (65).
Why: a commit is what a person can actually look at. There is no signing authority here to check against.
Rules out: signatures, and a quiet update that widens what a plugin may do.

## Agents and limits

**15. Every user action is an `Op`, with one exception.** Answering stays off `kg` (10).
Why: the `Op` list is the seam the CLI is generated from, so a feature with no CLI path does not compile.
Rules out: a second path that changes a thread without an `Op`.

**16. A thread has no message to attach a file to.** The person types into the program in the terminal.
Why: the program's own input is the line. Kagan does not wrap it in a message.
Rules out: an attachment cap, and a message field that accepts or refuses images.

**17. There is no send queue.** Stop ends the program. Nothing holds a message to send after it.
Why: the person types into the program.
Rules out: a queued message, and interrupt-then-send.

**18. There is no permission-mode picker.** A thread stores no permission mode.
Why: the program keeps its own permission choices.
Rules out: a picker, and a mode the host applies to the program.

**19. Child failure notices go to the sidebar parent.** A failed or interrupted child appends a notice on its parent. A stop the person asked for, and a success, stay quiet. The lifecycle owner gets no copy.
Why: the parent is where the person is reading. Noise for expected outcomes trains people to ignore the channel.
Rules out: notices on success, on a deliberate stop, and a second copy to the owner.

**20. Parent and lifecycle owner are write-once.** Both are set at spawn. Archiving or deleting the owner does the same to its dependents (`ON DELETE CASCADE` on `lifecycle_owner_thread_id` in `crates/store/src/store.rs`). Parent is sidebar nesting only. `archive_span` counts visible unarchived lifecycle dependents.
Why: lifetime a person can reason about needs to be fixed when the thread is made.
Rules out: nesting deciding lifetime, and an `Op` that moves an owner.

**21. Spawn may hide a thread.** It stays reachable by id. Delete still asks the person (12).
Why: plugin and background work should not fill the sidebar.
Rules out: hidden meaning unprotected.

**22. Attention moves on idle, error, and a raised question.** Opening the thread marks it read.
Why: those are the three moments the thread actually needs the person.
Rules out: unread on every agent message.

**23. An agent process dying ends the turn in error.** The prompt stays consumed. The next message starts the agent again.
Why: re-sending a prompt whose side effects already happened is the worse failure.
Rules out: automatic retry of the dead turn.

**24. Two skills with the same name in one source are both dropped.** Also, `kg skill list` shows the error. A higher source overrides a lower one: bundled, plugin, user, project.
Why: picking a winner between two same-named skills would be arbitrary and silent.
Rules out: first-wins or last-wins within a source.

## Plugins at runtime

**25. A slow plugin is marked, not unloaded.** `crates/plugins/src/watchdog.rs` marks it after repeated renders average more than `BUDGET` (16 ms) and the plugin row offers to disable it. Each plugin has its own QuickJS VM (`ShellRuntime::new_isolated_with_components` in `crates/plugins/src/lib.rs`), and every VM runs on the UI thread. gpui-shell cuts off one call that runs past its budget: 50 ms for render and layout, 500 ms for an event handler or a job, 5 s for loading (`Budgets` in gpui-shell's `engine/quickjs/sandbox.rs`). The JIT honours the same cut-off. The watchdog sees render time only, because gpui-shell's `RuntimeMetrics` does not time jobs or events.
Why: a stalled frame of up to 500 ms is visible but recoverable, and the person, not a timer, decides to disable a plugin. Heavy work belongs in the `process` area. The `downloads` area and `powers.spawn` were removed because no plugin used them (65). The `audio` area is superseded by 42.
Rules out: unloading on the third slow render. Moving jobs to a worker thread needs a gpui-shell runtime with no window, and stays open work.

**26. One 10 second grace.** `GRACE` in `crates/core/src/workspace.rs` covers both archive and worktree removal. Both deadlines persist across a restart. Archive never touches files; it stops the run and retires a worktree.
Why: long enough to undo an archive, short enough that a worktree does not linger. One number is one thing to reason about. Archive is reversible, so it must not delete work.
Rules out: separate timers, immediate removal, and deleting a personal folder on archive.

**27. Removal deletes only folders kagan created, and a personal folder only on Delete.** Archive and the grace retire a git worktree under the data directory, and only after the grace. A personal folder is never removed by archive, the grace, or a restart. `ThreadOp::Delete` removes it, and only when nothing else is in or on it: no other thread, project or environment whose path lies in the folder or contains it. Delete asks a person first, and the question names the folder and what is in it. The final check and the deletion are one database commit, so a Run or project add cannot attach between them; until the removal finishes, a new thread or project in that folder is refused. A deletion interrupted after its commit is finished at the next start. A project checkout is unmanaged and never removed.
Why: the one rule a person can hold is that kagan does not delete work on archive, and deletes a folder only after a person names it.
Rules out: removing a checkout, deleting personal files on archive, and keeping personal folders forever. Delete of a personal folder that another thread, a project, or a nested environment uses keeps it.

**28. A dirty worktree is never force-removed.** `remove_folder` in `crates/core/src/environment.rs` runs `git worktree remove` with no `--force`. A refusal sets the environment to `error`, stores the reason, and the archived page names the files that blocked it and offers Remove again. `kg environment get` includes that reason. Remove again runs only while that status is still `error`, and returns the refusal when the folder is still there. Restore, and a setup that becomes ready, clear the reason. While it is set, Delete is refused and the row is not reused as a failed setup. A clean removal deletes the folder and leaves the branch, so Restore can add it back.
Why: uncommitted work is the one thing that cannot be recreated.
Rules out: forcing after the grace, and deleting the branch with the folder.
Exception, by design: `abandon_worktree` does force, only when `git worktree add` itself failed, on a folder that never became a ready environment. Project removal (decision 71) is another: it forgets the project, so a refused folder stays with no Remove again. Its warning names the folder path and the `git worktree remove` command that finishes it.

**29. One app take on the microphone.** Superseded by 42. The voice files are gone.

## Platforms and release

**30. Linux, macOS and Windows run on every pull request.** `.github/workflows/ci.yml` runs the checks on Linux, and clippy and the tests on macOS and Windows, for every pull request and every push to `main`. A diff of only docs, the book and markdown skips the Rust jobs. Mutation testing runs only on a manual dispatch. The repository is public, so this is the only CI; CircleCI is gone.
Why: GitHub Actions is free for public repositories, and code behind `cfg(windows)` or `cfg(target_os = "macos")` needs a run on that system before it merges.
Rules out: a label or a `full` parameter for macOS and Windows, and a second CI service.

**31. The in-app browser is removed.** It was unused. The window never showed a browser view (32, 47), every driving command failed before it could reach a page, and no plugin called the host function that opened one. `kg browser` is not a command. `openUrl` still opens the system browser.
Why: a command that cannot show a page is surface with no user.
Rules out: bringing that browser back, and a Linux web view as a way to replace it.

**32. The page does not host a web view.** There is no load event, and nothing to fork a web view to fix. Part of it is superseded by 47: there is no page. The browser commands that assumed a view are removed (31).
Why: the cost would be a fork of someone else's web view, forever.
Rules out: that fork.

**33. Nothing opens a browser popup.** The page does not host a web view, and `Workspace::push_browser_tab` is gone. The browser commands that opened tabs are removed (31).
Why: a second OS window from a web page is not something the person asked for.
Rules out: a popup window.

**34. A program already on `PATH` is listed where it is.** Nothing is downloaded for it and it has no Remove.
Why: kagan did not install it, so it must not offer to uninstall it.
Rules out: shadowing a `PATH` program with a managed copy.

**35. Running the release workflow on `main` is the release.** Start the Release workflow from `main` and type the version (decision 98). It creates the tag on the current `main` commit, stamps the version into the build without committing it, and publishes GitHub-generated notes with the installers and `SHA256SUMS`. A tag by itself does not start the workflow. The macOS disk image holds one universal app for Intel and Apple silicon. It is unsigned and not notarized unless the Apple secrets are set: `APPLE_CERTIFICATE` signs it, and `APPLE_ID` notarizes it. The workflow still publishes the file. The Windows installer is unsigned unless `WINDOWS_CERTIFICATE` is set. The Linux packages are unsigned. After a release that is not a prerelease, the workflow writes `Casks/kagan.rb` of `kagan-sh/homebrew-tap` with the version and checksum of the universal disk image, with the deploy key in `HOMEBREW_TAP_DEPLOY_KEY`.
Why: one source for a version, and no commit that exists only to say what the tag already says.
Rules out: a committed version to keep in sync, a draft release, hand-written notes, releasing off a branch that is not `main`, and treating a hand-pushed tag as the release.

**36. Reading a pull request, change counts, or the folder from the CLI was removed as unused.** The strip and its poll were already gone. No window called `kg environment changes`, `pull-request`, or `open`. The window reads the diff through `DiffOp`. Agents run `git diff` and `gh pr view` themselves. `branches` and `set-base` stay, because the start screen and the branch diff use them.
Why: the page does not keep a last answer on screen, and the three commands had no caller left.
Rules out: a strip, a timer, and those three commands.

**37. A phone is a thin native client per platform until GPUI runs there.** SwiftUI on iOS and Jetpack Compose on Android, each showing threads, the terminal, events and approvals (10) from the person's own host over the `Op` protocol (1). The host listens on `127.0.0.1` only; Tailscale Serve is the way in. Pairing is a short-lived single-use code shown on the desktop, and the device list can revoke a phone. When Zed's iOS backend ([zed#63068](https://github.com/zed-industries/zed/pull/63068)) merges and gpui-kit takes it, the iOS client moves to GPUI; Android waits for an upstream backend the same way.
Why: GPUI has no merged iOS backend and no upstream Android one. Carrying either in our fork is a second product to maintain, and a phone is worth having before then.
Rules out: carrying `gpui_ios` or a community mobile backend in our fork, a web page as the phone product, binding anything but loopback, a relay we operate, and sharing UI code between the native clients and the desktop before GPUI runs on the phone. The plugin loopback port is removed: `powers.serve` is refused, and no plugin listener remains.

**38. Accepted as limits, not as work.** A restart drops standalone approvals (6). The page does not host a web view (32). The in-app browser is removed because it was unused (31), not left as a bug to wire up.
Why: each is cheap to live with and expensive to close.
Rules out: treating any of them as a bug report.

**39. An unread diff can ask for a line, and nothing is forced.** Superseded by 43. Preference `predict` is off unless set. When it is on, opening an unread file hides the hunks behind one line. Reveal works with the line empty. A written line is a `file.predicted` event shown above the diff. No score is stored.
Why: a forced gate is skipped and resented. A score invites gaming it. The baseline shows the diff at once.
Rules out: blocking reveal on the line, turning the preference on by default, and any tally or comparison of what was written.

**40. Attention is three numbers from the event log.** Superseded by 43. `opened` is the one new event, because switching to a thread was not recorded. An empty answer is stored, because the line share had no denominator; the thread still does not show it.
Why: the quiet features need a baseline, and a score would change the behavior it measures.
Rules out: a separate event for answers, per-thread charts, and treating a permission as accepting the work.

**41. Archived threads leave the sidebar.** They are listed on Archived, and restored from there.
Why: a retired thread is not current work. A permanent Unarchive control on every sidebar row is the wrong place for it.
Rules out: an Archived group in the sidebar.

**42. Native voice and the plugin `audio` area are removed.** Dictation, spoken replies, `Op::Voice`, the `kg-audio` crate, the `speech` feature, and the plugin `audio` area are gone. A manifest with `"areas": ["audio"]` is refused as an unknown area.
Why: plan D7 and D11 of ticket #79. A later vocodr plugin would bring its own speech programs. Those powers are not in this version (65).
Rules out: speech code in the host, and a host area for the microphone or speakers.

**43. The attention experiments are removed.** Prediction, the answer line, held news, and the attention report are gone. Opening an unread file's diff shows the hunks and clears its mark. A permission question shows its options; an answer stores the choice and the title, with no line. Other threads' status shows in the sidebar as it changes, and the title bar does not count them. The Usage page in this sentence is superseded by 44. `kg usage` is not a command; in part replaced by 268, which adds `kg usage show` and `kg usage refresh`. Old `file.predicted` and `opened` rows, answered events that still carry a `line`, and the `predict` setting still load. `opened` is no longer written.
Why: plan D8 of ticket #79.
Rules out: a gate before a diff, a sentence before an answer, holding sidebar news, and the three 7-day numbers.

**44. Usage leaves the host.** The page, the 24-hour roll-up, and the `usage_reports` table are gone. The title bar does not show a token count, and there is no `threads.context` result. A plugin may declare `powers.read` folders under the home directory. `kagan/files` reads a byte range inside read roots opened when the plugin loads, off the UI thread, because gpui-shell reads a whole file and has no offset.
Why: plan D35 of ticket #79. Scanning agent session logs is a plugin's job, and this cleanup adds no feature except the read power that plugin needs.
Rules out: a usage page or a stored roll-up in the host. Narrowed by 268: live provider limits may be shown, but no stored roll-up and no session-log scan.

**45. A thread runs the program the person picks, in its own terminal.** `ThreadOp::Run` creates the thread and its environment. The page starts the program in that folder. Each thread keeps its own pty; switching away leaves the process and the scrollback. Stopping the thread kills the process. There is no chat transcript and no provider link. On Linux the page is the standalone binary in `crates/window` until that page runs inside `kg`. The page parts are superseded by 47.
Why: the work is the agent program the person already runs, in the thread's folder, and a live terminal is what they type into.
Rules out: one shell for the page, opening a provider link in order to show a terminal, and storing the typed command on the thread row. The parts that make the page own the pty are superseded by 46.

**46. The host owns each thread's terminal.** `ThreadOp::Run` starts the program in the thread's folder inside the host, in a pty, and `core` keeps it until the thread stops, is archived or deleted, or the program exits. The `kg-terminal` crate runs the pty and keeps the screen in memory. It answers the program's terminal queries, such as the cursor position, itself, whether or not a client is attached. A client never sees raw output. It asks for a screen (`ThreadOp::Screen`), sends keys (`ThreadOp::Input`) and sets the size (`ThreadOp::Resize`), and hears `WorkspaceEvent::Screen` when the screen changes, at most about 30 times a second. The window is one such client. Closing it leaves every program running. Quitting kagan ends them. Amended by 269: on Windows and Linux, closing the last window quits kagan, and macOS keeps this behaviour. Opening the app starts a thread left running again (171): a thread left stopping is marked failed. The Linux preview in `crates/window` is gone (47). How a program ended is recorded: exit 0 is `exited` with its code and the thread goes idle; any other exit code or a signal is `exited` plus `failed` and the thread goes to `error`, which asks for the person's attention; an explicit Stop is `stopped` and idle, with no attention; a restart while a program runs marks the thread failed with "kagan quit while the program was running". `kg-terminal` reports the code or signal (`Exit`) without reaping the child, so the pid stays kagan's until its process tree is killed. A program's end is its process exit, not its pty closing: a program that closes its stdio and keeps running stays `active` until it exits or is stopped. A natural exit and a Stop run the same cleanup (questions, busy, terminal), and each records its own event. When a program ends, core keeps its final screen and scrollback (10,000 lines) without the pty, so a failure nobody watched stays readable; input and paste are refused, while screen, scrollback, scroll, selection and copy still work. Stop on an ended thread keeps the screen. The screen is released on delete, and when an archived thread's grace ends. It is not kept across a restart. Stop on a running program marks the thread `stopping`, ends the program, and keeps its final screen; its exit then records `stopped`, so a stop and a natural exit stay distinct. A finished screen follows its output until the reader has ended, so late output still reaches the window. A finished screen no longer asks for the mouse, so wheel and selection stay with the window.
Why: the host is what `kg` and a phone talk to (1), so the terminal has to live there. A client that owned the pty could not give it to a second one, and a thread with no window open had nobody to answer the program's queries.
Rules out: a pty owned by a window, a client that answers the program's queries, and a client that reads raw program output. Known limits: a screen is the visible rows only, so scrolling back stops working until a client draws from the host's history; every update sends the whole screen; each terminal has one size, set by the last client to resize; `ps` runs on the main thread on each drop (about 10 ms with 850 processes); a process that calls `setsid` itself escapes the tree kill; Windows kills only the leader; the exit can be seen before the last output is read, so a large error printed right before exit could be cut from the final screen. The Linux preview in `crates/window` runs one shell of its own through `kg-terminal` and shows no threads, until the page runs inside `kg`.

**47. The window is drawn by GPUI, on every platform.** The Kagan window is GPUI code in `crates/ui`, with no web page or web view on any platform. Its terminal paints the host's grid in process, read through `Workspace::grid`. Remote clients keep `ThreadOp::Screen`. Keys go through `ThreadOp::Input`, and size through `ThreadOp::Resize`. The terminal repaints on `WorkspaceEvent::Screen`, for the shown thread only. `kg` opens the window on Linux as well. This replaces the page parts of 32 and 45.
Why: a page drawn on top of GPUI forked a web view for each platform, and Linux had no window. A GPUI terminal reads cells in process, so it needs no ANSI round-trip. The rule in 46 that a client never reads raw program output still holds.
Rules out: a web view in any platform's window, and parsing ANSI frames in the UI.
Not in this slice: the diff view and the plugins box, which are reachable through `kg diff` and `kg plugin` for now. Also not in it: scrollback, mouse reporting, text selection and copy, and visual polish beyond the theme tokens. Off macOS the window's default shortcuts are Ctrl+Shift chords, so the program keeps every bare Ctrl key. A saved override can still take a bare Ctrl chord from the program, as the person chose.

**48. The right sidebar is a tab bar of panels, with two kinds of panel.** Built-in panels (Questions, Changes, Details) are native Rust views and show as non-closable tabs when their content applies. Plugin panels placed `right` (decision 59) are closable tabs. A trailing `+` opens a menu of the Browser, a terminal and the declared right panels that are not open yet (118). One selected tab's body fills the column. While the column is drawn, a Full screen button at the end of the tab bar lets it take the window beside the rail, in place of the threads and the terminal, until it is pressed again, the column closes, or a left tool or page opens; it is window state, not a preference. Plugin install and management live in the left sidebar's Plugins section (decision 57), not here. The thread mark "needs you" is attention, and it is not this panel. The sidebar can be collapsed with `secondary-\`. Its open state is the `main.right-sidebar` preference, changed through `PreferenceOp`; an open window reads it when it opens, so a change made from `kg preference set` applies at the next open. Its width is kept when it closes and opens again, within a drag range of 240 to 560 pixels. Questions lists every pending question of every thread, hidden threads included, and standalone approvals. A question on screen when the person starts typing stays up; a question that arrives while they type is held until they pause for 1.5 seconds, and the panel says how many wait. The 1.5 seconds is a design value, not a number from the research. Iqbal & Bailey (CHI 2008) is cited for holding interruptions until a breakpoint; it does not give this number. Not re-checked here. Changes lists the shown thread's changed files, in the uncommitted or branch scope, as compact rows with the kind, the counts, and the selected row. Opening a file shows its review in the center (decision 60). It re-reads the open thread every two seconds; a read that is running is not started again, and one request that arrives meanwhile is taken after it. Nothing marks a file as the agent's (decision 60).
Why: a tab bar matches how people open side tools, keeps built-ins and plugin panels in one place, and holds the Browser and extra terminals too (117, 118).
Rules out: docking, zoom, and a saved multi-panel accordion layout. Bottom plugin panels are not in the window. Decision 59 places a plugin panel left, center, or right.

**49. A thread's program knows it runs inside kagan.** Every thread's program gets `KG_THREAD_ID`, `KG_PROJECT_ID`, `KG_ENVIRONMENT_ID` (when the thread has one), `KG_CLI`, `KG_SOCKET` (when the app set one), and `PATH` with `kg`'s folder first. The host sets these in `crates/core/src/thread/agent.rs`. A program whose first word is `claude` also gets, before the person's own arguments: `--mcp-config <dataDir>/agent/threads/<id>/mcp.json` (the `kagan` server, `kg mcp --thread <id>`), `--plugin-dir <dataDir>/agent` (a plugin named `kagan`, whose `skills` folder holds the bundled skills and the enabled plugins' skills, one folder each), and `--append-system-prompt-file <dataDir>/agent/threads/<id>/note.txt`, then `--session-id` or `--resume` for the thread's conversation (decision 54). A program whose first word is `codex` gets the same server as `-c mcp_servers.kagan.*` overrides. Codex has no per-run skills folder. The fixed note also goes in the `kg mcp` server's instructions, which reach both programs. A `claude` line whose first argument is a subcommand gets none of the extra arguments (the Claude CLI's commands table). Rules out: an include list, `--force` on that removal, a sweep of every process in the folder, a new provider, and skipping the script on Windows when `sh` is missing.
Known limits: Restore of a worktree that was deleted and added back does not run setup again. A setup that fails to run is reused for the next worktree in that project until the script succeeds, so a second worktree is not created while one is waiting. A mismatch, including one found on Retry, is deleted instead, so the next start resolves again. When the script process ends, its own process group is closed; that is not a sweep of the folder.

**97. The grid is built when it is read, not after every read.** After each read from the pty, the reader parses the bytes and only marks the screen changed: it moves the version forward, keeps the title, answers queries and applies queued edits. A read that finds the reader parsing gets the last grid and never waits; the reader then builds the next grid after its chunk. `ThreadOp::Screen`, the transcript and the stored screen (decision 62) read the screen itself and never needed the grid. Versions still move only forward, and synchronized output, its timeout, the title and the selection are unchanged.
Why: the reader copied the whole 120×40 grid (about 35 µs) after every read, while the window draws at most 30 to 60 frames a second, so most copies were never drawn. Measured on this Mac (arm64, macOS 27.0.1, release, 120×40, medians of 9 alternating runs; inputs from the libghostty spike), alacritty before → after: 50 MB of mixed text and color through the reader loop with a frame asked for 60 times a second, 99 → 184 MB/s; 1,000 full-screen truecolor frames, 143 → 311 MB/s; one status row rewritten 100,000 times in 64-byte writes, 28,000 → 3.2 million updates a second; the same two files through a real pty with `cat`, 21 → 129 MB/s and 26 → 119 MB/s. One grid build alone is 31 to 37 µs before and after.
Rules out: a grid copy per read, and a frame that waits for the reader's lock.

**100. **101. People and plugins add themes.** This changes 56 for `themes` only; every other refused spot stays refused. Settings → Appearance → Theme shows one card per theme: the built-in ones, then each `<dataDir>/themes/<id>.json`, then the themes of enabled plugins. Each card shows three of its colors, its name, and where it comes from: Built in, Your file, or the plugin's name. A file that does not load shows its id and the error on its card and cannot be picked; the other cards still work. A plugin manifest declares `"themes": [{ "id": "midnight", "file": "themes/midnight.json" }]`. The file is inside the plugin folder and uses the schema of a person's theme file (`kg_domain::ThemeFile`, which `kg-ui` and `kg-plugins` share). Install, update and `kg plugin check` refuse a bad id, a repeated id, a path outside the plugin and a file that does not parse, naming the theme and the file. A plugin theme's id is `<plugin id>/<theme id>`, so it never clashes with a built-in or file id; `kg theme set` accepts that form. A theme needs no power and adds no line to the install screen. The catalog follows the plugin host: disable, update, reload and removal drop or re-read its themes. `kg theme new <id> [--from <theme>]` (`ThemeOp::New`) writes a copy of the chosen theme, or of `--from`, to `<dataDir>/themes/<id>.json`, named "\<name> copy", and prints the path. It refuses a built-in id and never overwrites a file. It runs in the window process, which holds all three sources; plugin themes join that list once a window has opened. `kg theme folder` (`ThemeOp::Folder`) makes the folder when missing and prints it; core answers it, so it needs no window. Every theme file, a person's or a plugin's, is read only when it is a regular file of at most 64 KiB, and its name is one line of at most 64 characters; anything else is an error on its card and refused by the plugin checks, so a pipe or a huge file cannot stall the window. The Theme row offers New theme… and Open themes folder (actions `NewTheme` and `OpenThemes`, without a default key): the first writes `<id>-copy.json`, then `-copy-2` and on, for the theme in use, and opens it with the system; the second opens the folder. The folder is still read on the background executor every 500 ms, never in render, so a saved file shows within a second. When the chosen theme's file stops loading, the window keeps its last good colors and says so once in a toast, not again for later errors in the same theme until it loads; when a chosen plugin theme goes away, the window uses the default, keeps the id so the theme returns with its plugin, and says so once. A chosen theme that was never loaded still shows the missing line under the cards and no toast. A theme file may also carry a top-level `look` object, the same in both modes: `space` (`xs`, `sm`, `md`, `lg`, `xl`, `xxl`), `radius` (`xs`, `sm`, `md`, `lg`), `type` (`caption`, `small`, `body`, `title`, `mono`), `row` and `control`, all whole pixels. Every field and the object itself are optional; a value outside `space` 0 to 64, `radius` 0 to 32, `type` 8 to 48, or `row` and `control` 16 to 64 is refused with the field named, so a zero-height row or an unreadable size cannot load, and a file without `look` keeps the density and type the window has today, so an older file parses and paints exactly as before. `deny_unknown_fields` still holds, so a file written by a newer kagan with a field this version does not know is refused with the field named rather than painted partly. The palette also gains optional `selection` (default `raised`) and `input` (default `line`). The host reads `look` through one projection; `ThemeConfig` only carries the mono size and the two radii, and a plugin web panel gets every value as a CSS custom property.
Why: a person could write a theme but not find it in Settings, and a plugin could not ship one, though the format was already a file.
Rules out: a theme that runs plugin code, a plugin theme that replaces a built-in or file id, overwriting a person's file, and a file watcher thread (the half-second read already meets a second, and the GPUI tests drive it with the test clock).

**102. Every plugin command is in Settings → Keyboard.** Amended by 222: a built-in shortcut can be left with no key. Keyboard lists the built-in shortcuts as before, then one group per enabled plugin with commands, titled with the plugin's name, with one row per declared command, keyed or not. A row shows its key, or Not set. Change (Bind on a row with no key) waits for the next key and saves it through `kg keymap set`; Escape stops without saving, and the key does not run its action. A plain key or a bare Ctrl key belongs to the program, so it stops waiting, saves nothing and the row says "That key belongs to the program."; a key with Command, Option or Alt, Ctrl and Shift, or F1 to F35 is saved. Remove saves no key on a plugin row; on a built-in row it saves an empty key, and Reset puts the default back [decision 220]. A refused save shows "\<key> is already used by \<shortcut>." on the row. A plugin key that a window shortcut takes is not bound, as before. Between plugin commands, a key the person saved always wins over any plugin's manifest key, whatever the plugin order, so a plugin installed later cannot take it; between two manifest keys, or two saved ones, the first in plugin and command order wins. A plugin command whose key is not bound shows Not set with that sentence, and the row that took the key says "\<command> in \<plugin> also wants this key." Disabling or removing a plugin takes its rows away. `kg keymap` covers plugin commands as `<plugin-id>:<command>`: `get` adds `plugins`, each enabled command with its key or null; `set` gets the same key-name check as a built-in; `remove` is new; for a built-in it saves an empty key. A conflict is named the same way, `NewThread` or `<plugin-id>:<command>`. The keys are still stored with each plugin (`$hotkeys`), so saved ones carry over; only the command changed. `kg plugin bindings` and `kg plugin set-binding` are removed, and with them `--replace`: remove the other command's key first. This supersedes the last sentence of decision 69. `kg plugin new` writes the `hello` command with no key: any fixed key clashes with the person's second starter, and a key picked free at that moment can clash with the next plugin installed.
Why: a command with no key, or whose key was taken, appeared nowhere in the window, and every starter asked for the same key, so the second one lost it in silence.
Rules out: a command palette.

**103. A plugin index lists plugins by name.** This builds the marketplace of 3. An index is `.kagan/index.json` in a git repository, read at `git:<url>@<ref>`, or a JSON file, or a folder holding `.kagan/index.json`, on this computer. It holds `schemaVersion` 1, a `name`, and `plugins`, each with a `name`, a `description`, a `source` (what `kg plugin install` takes) and an optional `plugin` (its `--plugin`). A path is inside the folder that holds `.kagan/`, or the file's folder. The index name and each plugin name are 1 to 64 lowercase ASCII letters, digits, `-`, `_` or `.`, because they show on the approval card: no line breaks that fake card lines and no lookalike letters. A description is one line of at most 300 characters. Unknown keys, a repeated name, a git source without a ref, a ref that starts with `-`, a path in an index read from git, a path that leaves the index's folder, and a file over 1 MiB (checked before git prints it) are refused. Git runs with `GIT_ALLOW_PROTOCOL=https:ssh:git:file`. `kg plugin index add|list|remove` and the Indexes card in Settings keep an ordered list in `<dataDir>/indexes.json`. Add reads the index first and refuses one it cannot read, or one whose name an added index already uses. A saved list that cannot be read is an error, and nothing saves over it. Every index address that `kg`, Settings, a warning or an error shows has its password removed, and an http or https user name too. `kg plugin search [<text>]` and the card's search list the plugins whose name or description holds the text, ignoring case. An index that cannot be read, or that reuses an earlier index's name, is one warning, and the others still answer. `kg plugin install <name>` and the card's Install take a source that is neither `git:` nor an absolute path as a name; `kg` sends a path only when it exists. `<index>/<name>` looks only in the first index with that name, so a later index that renames itself cannot stand in for it. `--plugin` with a name is refused. The indexes are read in order and the first that lists the name wins. An earlier index that cannot be read stops the install, so a later one cannot stand in for it. Then the same install runs: one at a time, and the same approval card. The install and update cards now say where the code comes from: `From <url> at <ref>, commit <full commit>`, without a password, and the index that listed it with its address. A caution line follows when the code is a folder, or a repository whose host and owner (the first part of the path) match no index the person added; that is how this decision reads an unknown host. The record keeps the git source and commit (14), not the name, so update and a later edit to the index never move an installed plugin. Indexes are read only when a person or a command asks, and nothing installs or updates on its own. `kg plugin share [<path>]` checks the plugin, refuses uncommitted changes in its folder or a commit no remote branch holds, and returns a typed index entry (`name` from the last part of the id, the first line of `instructions`, `git:<remote>@<full commit>`, and the folder from the repository root) and the `kg plugin install` line. It pins the commit it checked.
Why: teammates could install a team plugin only by pasting its git address and ref, and could not see which commit they approved.
Rules out: an index fetched over plain HTTPS (it cannot use the person's git sign-in for a private repository), a hosted catalog, ratings, signing (the pinned commit already fixes the code a person approved; a signature would only prove the author and needs keys on every machine), share writing into an index file, powers or commits listed in the index (the approval card and the commit stay the gate), and installing or updating from an index without a person.

**104. A plugin setting can be a secret.** A `secret` setting holds a token, such as an API key for a `powers.fetch` host. Settings shows a masked field with Set, or Replace and Clear once one is set. The field is empty after each save and never shows the saved text, and `kg ui` reports eight dots whatever its length. `kg plugin config <id> set <key>` with no value asks at a prompt that does not show what is typed, or reads one line from stdin, so the text stays out of shell history. `kg plugin config <id> clear <key>` forgets it. `get`, Settings, `kg ui`, thread events and `kg diagnostics export` say only `"set"` or `null`, so an agent in a thread cannot read it through `kg`. The plugin reads the text from `host.settings()`. kagan writes `[secret]` in place of the exact text everywhere it leaves the plugin: the plugin log, a load or view error (`kg plugin list`, `kg status`, the panel's failure), a tool reply or tool error, a toast, and `kg <cli>` output. Only the exact text is found, the longest secret first; a split or encoded copy is not. A secret is one line of at most 1024 bytes, because Windows Credential Manager holds 2560 bytes of UTF-16, and its key is at most 64 bytes, because the key is in the keychain account name. Removing the plugin forgets its secrets, even when its folder is gone; a key the keychain refuses to delete is named in a warning, and the plugin is removed anyway. An update that drops a secret setting forgets that secret.
Where it is kept. The keychain is opened the first time a secret is read or written, off the window's thread, and that connection is kept for the whole run:
- macOS: the login Keychain. An item belongs to the app that wrote it, so another program needs the person's OK to read it.
- Windows: Credential Manager, under the person's Windows account.
- Linux: the Secret Service (GNOME Keyring, KWallet) when the session has one. If the service restarts while kagan runs, secrets fail until kagan restarts. When it cannot be reached in a run, a key it holds is neither replaced in the file nor forgotten: setting it fails, and removal names it in a warning.
- Otherwise: `<data>/secrets/<plugin id>.json`, with the folder set to 0700 at each save and the file 0600. Settings and `kg` say plainly that the secret is in a file other programs run by the person can read.
The entry is service `kagan`, account `<plugin id>/<key> in <data dir>`, so a second kagan with its own `KG_DATA_DIR` keeps its own secrets. `<data>/secrets/<plugin id>.json` also lists, by name only, the keys the keychain holds, so removal finds them without the plugin's manifest. Tests never pick a keychain, so they use the file, or an in-memory keychain.
Why: a token in a `string` setting was printed by `kg plugin config get` to any caller, every agent included (parity report, item 3).
Limits: a program running as the same person can read Credential Manager, the Secret Service and the file. The macOS Keychain asks before another program reads the item, but not before kagan does, so an agent that edits an installed plugin's code on disk and reloads it can have that code read the secret. An unsigned macOS build asks again after each rebuild. The hiding finds only the exact text: a plugin that splits or encodes its secret can still show or send it, and a secret the plugin draws in its own view, or passes to a thread it starts, is shown as is; and its declared `fetch` hosts and `run` programs bound where it can go. A setting that changes from text to secret has its old value overwritten in the database, but SQLite can keep the old bytes in free pages until it is compacted. A value piped on stdin is always text, so `kg plugin config set` of a boolean takes its value on the command line. Plugins load one after another, so an unanswered Keychain prompt holds the plugins after it. The install screen does not list a secret setting, because it grants no power. On Linux the Secret Service adds its own client crates to the build.
Rules out: a secret in the database, and a person-only question to type it in, which today's questions cannot carry. A value typed on the command line still works, as for any setting; the docs and `--help` say to leave it off.

**105. The person may let a plugin draw the thread list or the review.** This amends 2, 56 and 70. A manifest panel may say `"replaces": "threads"` (placed `left`) or `"replaces": "review"` (placed `center`); one panel per slot, and `kg plugin check` refuses anything else. A replacement panel is not a rail tool or a page. Settings → Appearance has a Sidebar and a Review row: Built-in, or each enabled plugin that offers that slot. The choice is the preference `slot.threads` or `slot.review`, `kagan` or a plugin id. The window sets it directly. `kg plugin use <slot> <plugin|kagan>` sets it too, and asks a person first when it names a plugin and comes from a terminal or an agent; `kg preference set slot.*` from a terminal is refused. Installing, updating, enabling or reloading a plugin never changes the choice.
The plugin draws only the body, clipped to its frame: the rail, New thread, the Archived footer, questions, approvals, the waiting count (on the Threads rail button while a plugin draws the list), the review header and the review footer stay the host's. A replacement view may not use a component that draws above the window (Popover, HoverCard, Tooltip, DropdownMenu, DropdownButton, Menu, MenuBar, Select, Combobox, Popup, DatePicker, Dialog, AlertDialog, Sheet, Notification, NativeMenuTrigger). The built-in comes back at once, and the plugin log and the window say why, when the plugin is off or removed, stops offering the slot, fails to start or to load the view, its view throws (a render that runs past gpui-shell's 50 ms budget, or a load past 5 s, throws), or it uses one of those components. The saved choice goes back to `kagan`, so it never returns on its own. A note must name a changed file of that review and hold at most 4 KiB; the front window, whose context the plugin reads, answers it once. Notes join the host's: only the host's footer sends them, through the same paste as the built-in review, and only its Discard clears them. The `threads` power now reads changed files and screen text too, and the install screen says so ("reads, starts and changes your threads, reads their screen text, and reads their changed files"). Why: people want a different thread list or diff without forking kagan, and the parts that keep a person safe (approvals, attention, what gets sent to the agent) must stay drawn by the host.
Rules out: a plugin switching a slot by itself, an agent switching it without a person, a plugin drawing approvals in the host's place or over them, a review plugin that sends or discards on its own, and a slot that silently stays broken.

**106. No upgrades from pre-release builds.** kagan starts fresh at its first public release. This supersedes the migration parts of 5, 18, 31, 48, 58, 65, 67, 68, 69, 70 and 96. The database schema is an append-only list of migrations, `MIGRATIONS` in `crates/store/src/store.rs`, that sets an `application_id` of `0x6b676e31` ("kgn1") and a `user_version` equal to the number of migrations applied. Migration 1 builds the original tables and is never edited, so a fresh database still runs it and then 2, which adds `threads.conversation` (decision 54), 3, which drops `threads.model` and `threads.reasoning_level`, and 4, which adds `projects.sort` and backfills it. Migration 1 keeps the two dropped columns only because it is already applied wherever kagan has run. Later migrations are appended to that list, and the list in the code is the current one. kagan reads the 100-byte SQLite header with plain file reads before SQLite opens the file. An empty file, or a header with `user_version` 0, no kagan `application_id` and no schema, gets the schema. A file without kagan's `application_id` is refused without being opened, so its bytes stay the same and no `-wal` or `-shm` file appears: with a nonzero `user_version` it was made by a pre-release build ("\<path> was made by a pre-release build of kagan and cannot be opened. Nothing was changed. Move it, and any -wal or -shm file beside it, out of that folder, then start kagan again for a new database"); otherwise it belongs to another program ("\<path> is not a kagan database, so kagan did not open it. Nothing was changed. Move it out of that folder, or set KG_DATA_DIR to a different folder"). Only a file with kagan's `application_id` is opened, read-only, to check for a newer `user_version` as in 62. When opening fails, the app shows the message in a small window with Quit, answers each `kg` request with it, and quits when the window closes. Nothing moves `~/.makerspace`, renames `dev.makerspace` plugin ids, repairs worktrees from the old folder, reads `makerspace.json`, closes a turn an older build left open, strips removed areas from a saved approval, accepts a panel `height`, or refuses the retired theme id `default`. The thread record has no `seeded` or permission mode, and the database has no `acp_session_id`, `skills_fingerprint` or queued messages. Plugin databases keep their own `migrate`.
Why: only the maintainer has pre-release data, and code that upgrades it costs every later reader. The application id tells a pre-release file at `user_version` 1 or 2 from a current one, which the version alone cannot.
Rules out: upgrade code for a pre-release install, and kagan moving or deleting a person's old files.

Typing filters the rows by label, ignoring case. Enter runs the highlighted command from where the keyboard was, as if its key had been pressed there, and closes the list. Enter opens the thread and scrolls its terminal so that line is in view, when the terminal still has it. The search reads one thread at a time on the background executor; a new query drops the old search before its next thread, so typing never waits on it. A program that was running when kagan quit left no kept screen (62), so its text is not searched. Measured on 50 threads of 10,000 kept lines each: about 140 ms in a release build and 1.2 s in a debug build, off the window's thread, so there is no index.
Why: a person could run a command only by knowing its key or finding its button, and could find a thread only by its title in the sidebar, not by what its program printed.
Rules out: an index or a second store of terminal text, regular expressions, fuzzy matching, a plugin adding rows other than its commands, and running a command the list greys out.

**110. A thread can open extra terminals.** `kg thread terminal new` (Terminal in the right sidebar's `+`, Cmd+T) starts the person's login shell (`SHELL` with `-l`, or `COMSPEC` on Windows) in the thread's folder, in a pty the host owns through `Terminal::spawn` (46), with the same `KG_*` variables and `kg` on `PATH` as the program. Each extra terminal has a number in its thread, from 1, never reused while the thread lives, so a stale `--terminal 2` cannot reach a newer shell. The terminal Ops (`input`, `paste`, `screen` and the rest) take `--terminal <n>`; without it they reach the program, as before. The window shows each extra terminal as a tab of the right sidebar (118). Cmd+Alt+] and Cmd+Alt+[ (`kg window next-terminal`, `previous-terminal`) step through the terminals; × or Cmd+Shift+W (`kg thread terminal close`) ends one. A shell that exits closes its tab. Extra terminals are not the thread: they write no events, never make the thread busy, waiting, failed or needs you, and leave no screen when they end. Archive ends them when its grace ends (26), whether or not the program still runs, so Undo keeps them; Delete and Quit end them at once. They are not restored after a restart. Ending a terminal ends what its program started: its process group on macOS and Linux, and on Windows a Job Object (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`) the program joins after the pty starts it, terminated on Stop and closed when the terminal is dropped. Where that job cannot be made, Stop ends only the program, the reason is logged once and shown in `kg diagnostics export` (254), and a process the program starts before the job is assigned is outside the job (254). This holds for the program's terminal too; before it, Windows killed only the program.
Why: a person running an agent also wants a shell in the same folder for a dev server or a quick command, without a second app or a second thread.
Rules out: an extra terminal as a thread, a split view, restoring shells after a restart, a kept screen for one, and tabs over the program's terminal (118).

**113. kagan checks for updates when asked, and daily only when the person turns it on.** Check for updates is `UpdateOp::Check` (`kg update check`) and the action CheckForUpdates, in the kagan menu (Check for Updates…), the command list, and Settings → Updates (Check now). The version every crate reports is the one workspace version that the release stamps, so About and the check agree.

**114. Each install kind updates its own way.** kagan reads how it was installed from where it runs. A macOS `.app` from the dmg (`app`) replaces itself and restarts. A `.app` in an Applications folder while `<brew prefix>/Caskroom/kagan` exists, or one under a Homebrew prefix, is the cask (`homebrew`): the notice says `brew upgrade --cask kagan` with Copy command, and kagan never replaces it, so Homebrew's record and the app on disk never disagree. An AppImage replaces its file and restarts; `APPIMAGE` counts only when kagan's own binary is inside `APPDIR`, because a child process inherits both. A `.deb` or a source build (`other`) shows Update available and the release notes link only. When a check finds a version, one quiet line over the center names it, links its release notes, and offers Install when kagan quits and Restart and install… for the kinds kagan replaces, or the brew command, then Not now.
Why: two programs that both update one app fight, and a package manager owns what it installed.
Rules out: replacing a Homebrew, `.deb` or source copy from inside kagan, and asking for an administrator password to write a folder kagan cannot write.

**115. Only the person installs, and kagan refuses anything unsigned.** Installing is not an `Op`. Restart and install… and Install when kagan quits are window buttons that refuse `kg ui` input like person-only answers (93), and the question's Restart and install refuses it too; they call `Updater::download` and `Updater::replace`, which no socket command, plugin or agent tool reaches. An agent may run `kg update check` and `kg update status`; it cannot start an install or a restart. Restart and install… asks first, says those programs will stop and resume when kagan opens again (171), then downloads, checks the signature, puts the new copy in place, stops the programs as Quit does (66), and opens the new kagan once this process has exited (`open -n` on macOS, passing on the `KG_*` variables). Install when kagan quits downloads and checks it now and puts it in place during app shutdown, by any quit, including `kg window quit`, without opening kagan again; the state says which (`ready`, with `at_quit`). kagan bakes in one minisign public key. It reads `update.json` only after `update.json.sig` matches that key, and it refuses an archive whose signature is missing, unreadable, or made by another key. A replayed older list names an older version, which is not offered. Every link must be HTTPS, redirects included; plain HTTP is allowed only to this machine, for tests and local proof, because everything read is signed. `KG_UPDATE_URL` changes where the list comes from and never which key checks it. The release notes link is built from the version, not read from the list. A download stops at 512 MiB. Before downloading, kagan makes its staging spot beside the copy it replaces, so a folder it cannot write (the dmg, a translocated or read-only folder) fails at once and says to move kagan to Applications. The swap is one step: `renamex_np` with `RENAME_SWAP` for the macOS bundle, one `rename` for the AppImage. A failed swap leaves the running copy as it was. The replaced copy stays in the staging spot, and the next start removes it; the quit handler never deletes a folder.
Why: a restart ends every program in every thread, so it needs the person's yes, and a file from the network runs as the person, so it must come from kagan's release.
Rules out: an install or restart started by an agent, a plugin or `kg ui`, a key set at runtime, and an update that skips the signature for a test.

**116. The release signs the update files and publishes one list.** `.github/workflows/release.yml` packages macOS with `--formats app,dmg` so the bundle stays beside the dmg. Packaging builds without the key. A later step, which builds nothing, packs the bundle as `kagan_<version>_<arch>.app.tar.gz`, taking the arch from the dmg's name, and signs it, the exe and the AppImage with `UPDATER_PRIVATE_KEY` and `UPDATER_PRIVATE_KEY_PASSWORD` (minisign, through cargo-packager 0.11.8's signer); no dependency's build script ever sees the key. The publish job writes `update.json`: the version, and for `macos-aarch64`, `windows-x86_64`, `linux-x86_64` and `linux-aarch64` the asset URL and the contents of its `.sig`. A universal dmg's archive fills both `macos-aarch64` and `macos-x86_64`, and the job fails if a universal dmg has no archive; an Intel-only archive fills `macos-x86_64`; kagan asks for its own `<os>-<arch>` and finds nothing to offer when the list has none. - Settings and `kg env list` show each name with "Set", never the value.

Where values live:

- They sit in `<data>/environment.json`. The file is created with mode 0600 through a temporary file that is renamed over the old one.
- On Windows there are no mode bits. The file takes the data folder's ACL, and no test checks it.
- Values never go to the database, a reply, or the log.
- A project's value wins over the global one with the same name. Windows names fold case for that match; other systems do not.
- Removing a project removes its values. That step is best effort: a file that cannot be read is a warning, and the project is still removed.

Who gets them:

- A thread's program, its extra terminals, and its setup and teardown scripts get them. kagan's own names are set after them, so kagan's names are never overridden.
- Plugin processes and git do not get them.
- Setup and teardown scripts come from the repo, so they see global values from other projects too. The same program in the same folder already gets those values, and the setup file is pinned and checked before it runs.

Who may change them:

- A thread cannot change a variable. `kg env set` and `kg env remove` are refused when the request names a thread, which kagan's own terminals do. This stops the default path, not a determined agent: a program can drop `KG_THREAD_ID` and send the same request. A stronger check would need the connecting process's identity, and kagan does not record it.
- A name that is refused is refused before the value is read.

Writes and damage:

- Every read-modify-write of the file holds one process-wide lock, so two writes cannot erase each other.
- A file that cannot be read stops a thread start, and the error names its path. Setting or removing a variable moves that file aside to `environment.json.unreadable`, keeping its mode, and returns a warning that names the moved file.

Why not the keychain:

- Core cannot reach it. The keychain store is set up by `kg_plugins::init` (190). The platform crates live in `kg-plugins`, which `kg-core` may not depend on (`scripts/crate-boundaries.sh`).
- So these values use a file only the person can read. Plugin secrets fall back to a file the same way when there is no keychain (104).
- Plain text on disk: the values are not encrypted, and any program that can read the person's files can read them.

A later move to the keychain would take these steps:

1. Move the keychain store and its three platform crates out of `kg-plugins` into a crate `kg-core` may depend on. If that is a new crate, `scripts/crate-boundaries.sh` changes.
2. Store each value as one keychain item, keyed by its scope and name, and keep only the names in the file.
3. Read the existing file once, write each value to the keychain, and remove the values from the file.
4. With no keychain, keep the file as the fallback, with a warning, as plugin secrets do.
5. Amend decision 190.

Cost: product Rust is 73,498 lines on main. With this feature it is 74,652 lines, so the ceiling is 74,652 (up 1,154 lines, the gap this feature needs). `crates/ui/src/kagan/settings.rs` rises from 618 to 626 lines, so its own ceiling is 626.

Rules out: a value in the database, a value on the command line, a value in a reply or the log, a thread changing a variable through the op, and a second keychain path in core.

Claude's usage is asked the way the Claude Agent SDK asks it: kagan starts `claude` with `--output-format stream-json --verbose --input-format stream-json --no-session-persistence --setting-sources= --strict-mcp-config --mcp-config <file>`, where the file holds `{"mcpServers":{}}` and is removed when the read ends, in the person's home folder, with no terminal, and writes two control requests to its stdin, `initialize` and then `get_usage` with `skip_behaviors: true`. The reply lines give the `rate_limits` block, the plan (`subscription_type`, or the account's `subscriptionType`), and the account email. The process is stopped after 20 seconds. Why these flags: `--setting-sources=` (one token, with no value) loads no user, project or local settings, so the person's hooks and settings-listed plugins do not run. A test with a hook that touches a marker file showed the hook running with the default sources and not running with the empty list. `--strict-mcp-config` with an empty `--mcp-config` skips the MCP servers in `~/.claude.json` and the project. The installed CLI (2.1.322) accepts this set and answers both requests, checked with an empty config folder, so no account was used. On Windows the `claude` is usually an npm `.cmd` shim that runs through `cmd.exe`, so the flags avoid empty arguments and inline JSON: the MCP config is a file path. The empty value is one token, and a test pins the list on every system. Rejected: `--bare` (its help says Anthropic auth is only an API key or apiKeyHelper, so a subscription login is never read), and `--restricted` (it also removes the tools and confines file tools, which a usage read does not need). Not verified: `--no-session-persistence`. Its help says it works only with `--print`, and kagan does not pass `--print`; one manual read left no transcript in the home project folder, which does not prove the flag saves nothing. The flag is passed and tested as passed, not as effective. Still true after a read: the CLI reads its own login and `~/.claude.json`, and it updates its own state as it does for any use; kagan never reads, copies or refreshes the login. `get_usage` is experimental in Claude Code and its shape may change, so a missing `claude` shows "Claude Code is not installed on this computer.", a failed request shows "Claude could not give its usage. Check that Claude Code is signed in.", a timeout shows "Claude did not answer in time.", and a reply kagan cannot read shows "Claude sent a reply kagan could not read."; none of them is shown as 0%. A reply that arrives but is not followed by the process exiting within 20 seconds is discarded with the timeout. Quitting kagan during a read leaves the `claude` running until it exits on its own, which it does when its input ends. Codex is still read from its sign-in file, and that read is unchanged. Why: the popup covers both tools, and asking the installed CLI leaves Claude's token and Keychain untouched. Rules out: a Keychain read, reading Claude's sign-in file, a token sent anywhere by kagan, a refresh, and a Claude process started at start. Cost: product Rust went from main's 82781 lines to 83244 (+463).

**273. `kg ui` numbers only kagan's own windows: the main window and the About window.** The list comes from the handles kagan already keeps: the main window it opened and the About window it shows, kept only while each is open, sorted by `WindowId`. A plugin's windows, hidden or not, are never a target and never count, so a plugin that loads before the main window cannot move `--window 0`. The start-failure window (`failed.rs`) is not numbered either: it opens only when the workspace did not start, so the driver is not installed and no `kg ui` command can reach it. The list does not filter by root view type, because a window the shell opens through the component window opener kagan installs has the same root view type as kagan's own windows, so that filter would count it. Rules out: counting every open window, and picking windows by root view type. Cost: product Rust went from main's 83238 lines to 83254 (+16).

**274. A plugin can run in a hidden preview kagan that the person approves once.** This amends 238: `--offscreen` is also what a preview runs, and the person's app starts and owns it. It adds to 244: each preview has its own data folder, so one app per folder never refuses it. Why: building a plugin drove the person's own window, so the person could not work while an agent tested it. The approval is asked on the calling thread, in the person's window, with the same power lines as an install. The person's app then saves an approved plugin record and a `preview` marker into the new folder through `kg_core::seed_preview`, and starts `current_exe() --offscreen` with `KG_DATA_DIR` and `KG_SOCKET` set to that folder and `KG_THREAD_ID`, `KG_PROJECT_ID` and `KG_ENVIRONMENT_ID` removed. The reload watch is a `kg plugin dev` process the person's app owns. In a preview, a reload whose powers grew fails instead of asking, because no one can see the question, and the last approved code keeps running. Rules out: a socket call, flag or environment variable that makes an app trust a plugin; a preview that asks a question no one can see; a preview that shares the person's data folder; and a `preview` key that `kg preference` can read or write. Known limits: a folder is swept on the next start, not when the app quits, so one left by a quit stays until then; two starts that race can sweep each other's folder before either records it. Cost: product Rust went from main's 83254 lines to 83845 (+591).
