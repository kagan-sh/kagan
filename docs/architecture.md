# kagan architecture

Terms follow [CONTEXT.md](CONTEXT.md). Plugin shape: [plugin-api.md](plugin-api.md). Self-extend: [self-extend.md](self-extend.md). Why these shapes were chosen: [decisions.md](decisions.md).

## One program

One process per user holds the window, the database, and the plugin host. With no window open it keeps running; opening the app shows a window in that same process. `kg` run from a shell connects over a local socket (a Unix socket, or a Windows named pipe) and starts the process headless when none is running. The only adapter is in-process `Workspace::dispatch`. Nothing speaks a protocol beyond that socket.

## Async

GPUI's own executors only (`cx.spawn` on the foreground, `cx.background_spawn` for blocking work). No tokio. SQLite calls run on the background executor.

## Crates

Normal dependencies (dev-dependencies omitted). `cargo metadata` is the check.

```text

 │      │        │          ├──► terminal ──► process (Windows only)
 │      │        │          ├──► process
 │      │        │          └──► domain
 │      │        ├──► process
 │      │        └──► domain
 │      ├──► core
 │      └──► domain
```

The window is GPUI code in `crates/ui`: `kagan.rs` with `kagan/` and `terminal.rs`. `kg` opens it on macOS, Windows, and Linux. It has four parts. A title bar holds a button for each sidebar. A left sidebar lists projects and their threads, each with a status mark: a spinner while the thread is busy (CONTEXT.md) or stopping; a red dot when it failed; an amber ring when the thread needs the person; a filled square when it finished unseen; a muted dot when a live thread is idle, and a small hollow muted square when the program has ended (decision 63). The chosen thread's terminal paints the host's grid in process, read through `Workspace::grid` (decision 47). The title bar names the thread and project and offers Stop and the thread menu, or Restore for an archived thread. A program that has ended names the cause and offers Start again, which runs it again in its folder when asked. Save diagnostics is in that thread's actions menu, and on the ended line when the program failed, was interrupted, or its screen was not kept in full. New thread names a program and a project. Add project opens the folder picker. Remove project asks before forgetting the project and all its threads; it keeps the project folder and removes managed worktrees through git without force. A plugin panel placed `left` is one icon in the rail, and its body sits below the threads in the list column while it is open. A second click on that icon closes the body. A plugin panel placed `center` is a page under one title and Close; the selected thread's terminal stays, and Close shows it again. When the person picks it, a plugin panel draws the thread rows or the review body in place of the built-in, and the host keeps the rail, questions, counts and the review footer (decision 105). A review, a page, and Settings do not show together. Enter and Space do that only while Close has focus (decision 59). `kg surface list`, `open`, and `close` are `SurfaceOp`. A right sidebar (decisions 48 and 118) is a tab bar of Questions, Changes, Details, the open right plugin panels, the Browser and the extra terminals, with a `+` that opens the Browser, a terminal or a closed right panel. Details shows the shown thread's folder, program and git state through `ThreadOp::Details` (decision 111). A plugin panel is a left tool, a center page, or a right tab. Questions lists pending questions of every thread through `ThreadOp::Interactions`, and standalone approvals. Changes lists the shown thread's changed files through `DiffOp::List`; a file opens the center review, with uncommitted, branch and last-commit scopes read through `DiffOp::Show`. The review saves viewed marks as a preference and pastes notes to the shown thread through `ThreadOp::Paste` (decision 60). The command list lists every window command and plugin command with its live key, runs one from where the keyboard was, and searches threads through `ThreadOp::Search`, which reads each thread's kept rows through `Lines` on the background executor (decision 107). The rail offers New plugin…, which starts a Personal thread with the first installed agent and a prefilled prompt, and Manage plugins, which opens Settings → Installed (decisions 57, 72, and 80). When the window hides the right sidebar to keep the center at 480, its toggle draws those panels over the center's right edge, 320 wide, and does not change `main.right-sidebar` (decision 53). One selected tab draws its body. A plugin panel is mounted with `PluginHost::mount_panel` when it opens. A plugin panel that fails to draw shows Reload, Logs and Disable, with its stack trace behind Details, and the failure is written to the plugin log and reported by `kg status`. A question on a thread is answered through `Workspace::answer`. A standalone approval is answered through `Workspace::answer_standalone`. Questions are held while the person types (`Typed` from the terminal). The diff view is reachable with `kg diff` too, and plugins with `kg plugin`. `kg` opens the same window on Linux. The window reads threads through `Workspace` and observes its entities, so it does not poll SQLite. Its terminal sends keys through `ThreadOp::Input`, mouse reports through `ThreadOp::Report` (which keeps a scrolled view where it is), its size through `ThreadOp::Resize`, and its scroll, selection, copy and paste through `ThreadOp::Scroll`, `Select`, `Copy` and `Paste`. The grid it draws is the view the person scrolled to: the host keeps the history, the selection, and the scroll position. The terminal reads the host's screen as a grid built when it asks and the screen changed since the last grid; while the reader is parsing, it gets the last grid and the reader builds the next one after that chunk, so a read never waits on the pty (decision 97). Scroll, selection and paste edits wait in a queue that the reader applies before its next parse, so a client never waits on the reader. A window thinner than 20 by 5 cells keeps the program's size. Settings takes over the window: both sidebars hide, and the center shows one scrolling page of Appearance, Agents, Keyboard, and Plugins, with no search or section menu; Esc or the gear goes back and restores both sidebars. Its controls save through the same Ops as `kg` (`Theme`, `Preference`, `PluginOp::Config`), and it reads the state those Ops change, so a change from either one shows on the page. The two sidebars resize by drag, and their open state and widths are preferences (`main.left-sidebar`, `main.right-sidebar`, `main.left-width`, `main.right-width`, one set per window; `main` is the window). Shortcuts answer to the chord for their action: a saved override, else the default. Off macOS the default is Ctrl+Shift with the same key, so a bare Ctrl chord goes to the program. `FocusSidebar` moves the keyboard to the sidebar, where Tab moves between rows and Enter opens one. The macOS menu bar is `WindowOp`: About, Hide, Hide Others, Show All, Quit, Minimize, Zoom, and Close, plus Settings, the text actions, and the sidebar toggles. Quit from the menu, Cmd+Q, or the Dock asks when a program is running, then runs app shutdown, which ends programs still running (decision 46, decision 66). `kg window quit` does not ask. Close removes the window and leaves them running. A Dock click with no window opens it again (decision 66).

Rules:

- Every user-visible feature is an `Op`. The GPUI shell, the CLI, and plugin HostModules call `Workspace::dispatch`. The CLI is derived from `Op`.
- Only `core` depends on `store`. `ui` and `plugins` reach it through `core`.
- `domain` has no GPUI dependency, so the CLI parses without starting GPUI.
- Each crate is tested through its interface: `store` on an in-memory SQLite, `core` and `ui` with GPUI's test context.

## Programs

A thread runs one program the person names, such as `claude` or `codex`, in the thread's folder. Core starts the program in a pty and keeps its screen (decision 46). When the program ends, core keeps the final screen and the last 10,000 lines of scrollback without the pty, so the thread stays readable and input is refused. Once that screen has settled, core stores one replay of at most 4 MiB, tagged with the `Started` event of that run (decision 62). Opening the app reads it back through the same screen parser. A crash while the program is still running stores no screen, and the thread says no output was saved for that run. A stored row outside the geometry or the size bound is not turned into a terminal. The screen is released when the thread is deleted or its archive grace ends; the Kagan window is a client of that terminal. The cursor is not painted after the program has ended. Core records the program line on the thread. A program that cannot start leaves the thread failed with the reason. A program that exits with code 0 records `exited` and leaves the thread idle. Any other exit code, or a signal, records `exited` and `failed` and leaves the thread in `error`, which asks for attention. Stop marks the thread `stopping` and ends the program; once it has ended, the stop is recorded as `stopped` and the thread goes idle, with no attention. A terminal program has no turns, so neither exit nor Stop ends one. Stopping a thread that is still starting leaves it idle. Opening the app does not resume a program. A thread left active is marked failed with "kagan quit while the program was running", and a thread left starting is marked failed with "kagan stopped while the thread was starting". Saved events, including old messages, still load.

## Attention

Status of other threads updates in the sidebar as it changes.

Leaving a thread does not keep an unsent line. A thread is the program in its terminal.

## Commands

Built-in thread commands include `stop` and `archive`. A thread's work is the program in its terminal.

## Versions

Pinned in the workspace `Cargo.toml`, and upgraded on purpose:

- `gpui-kit` and `gpui-shell` come from one git rev of `kagan-sh/gpui-kit`, branch `kagan/upstream-rebase` (tagged `kagan-pin-<rev>`): upstream `longbridge/gpui-kit` with kagan's shell commits on top.
- On macOS and Windows, `crates/ui` builds `gpui-kit` and `gpui-shell` with the `gpui-fast` feature, so the window runs on GPUI Fast there (decisions 117 and 131). Linux stays on `gpui-pre`. `gpui-shell` keeps only its `quickjs` and `components` features: its `webview` feature stays off. A plugin `WebView` loads one page through `gpui-webview` directly, on macOS and Windows, the same path as the Browser tab. A web panel serves the plugin folder on `kagan-plugin://` through `gpui-webview` on macOS (decision 133). There is no general plugin browser and no address bar.
- That rev uses `gpui-pre` =0.3.10 for its upstream parts, and GPUI Fast (`gpui-fast` 0.1.12) when the `gpui-fast` feature is on, which it is on macOS and Windows. It needs Rust 1.98 (`rust-toolchain.toml`). Crates reach it through `gpui-kit`.

`gpui_shell::components::registry()` returns gpui-component's catalog unfrozen; kagan adds its own components and freezes it. `ShellRuntime::mount_exported_view` mounts a named exported view of a loaded application under the policy captured when that application's default export was mounted. That view is not a root: only the default export releases the generation, so closing a panel drops the view and leaves the plugin running. The view's `capturing` field and `dispatch_key_down` let the shell read capture and deliver a key without focus.

## Core interface

`kg` uses `<home>/.kagan` when `KG_DATA_DIR` is unset. `Workspace::open(data_dir, cli_path, cx)` returns a GPUI task that opens the database, restores the entity snapshots, recovers interrupted runs and installs the global. `cli_path` is the running `kg` executable. `Workspace::global(cx)` returns its entity. `Workspace::dispatch(op, cx)` returns `Task<Result<OpResult, OpError>>`; dropping a caller's task does not cancel an accepted operation.

`Workspace::project`, `thread` and `environment` return retained entities by domain id. Each entity exposes its domain `record()`. Observe the workspace for changed snapshots, or subscribe to `WorkspaceEvent::Event` for persisted thread events and `Changed` for other changes. `Open` asks the application to open a native window. The application subscribes before it starts plugins, and retains that subscription even when it has no window.

SQLite has one background worker on GPUI's executor. Opening the app does not resume a program. `kg-terminal` reports how a program ended (`Exit`: its code or signal), read without reaping the child; core records it as `exited`, and `stopped` for an explicit Stop. A thread left active is marked failed with "kagan quit while the program was running". A thread left starting is marked failed with "kagan stopped while the thread was starting". A settled screen is kept across that restart; a screen from a program that was still running is not. Saved events still load. A data directory from a newer kagan, or from a pre-release build, is refused before any write (decision 106). `kg diagnostics export` writes a local file and does not include terminal contents. It lists each thread's id, status, and structured cause, whether a screen was kept, and each plugin's id, kind, version, and warn and error counts. Titles, end text, plugin sources, and plugin log messages are omitted.

`Run` starts a thread whose stored provider is the program line, and starts that program in the thread's folder. `Input`, `Resize` and `Screen` are `Op`s on the running program's terminal, and `WorkspaceEvent::Screen` says a screen changed. A clean exit records `exited` and leaves the thread idle. A failed exit records `exited` and `failed` and leaves the thread in `error`. Stop marks the thread `stopping` and ends the program; once it has ended, the stop is recorded as `stopped` and the thread goes idle, with no attention. A terminal program has no turns, so neither ends one. Stopping a thread that is still starting leaves it idle. Opening the app does not resume a program. A thread left active is marked failed with "kagan quit while the program was running", and a thread left starting is marked failed with "kagan stopped while the thread was starting".

New worktrees live under `<data>/worktrees/<project>/<requested-branch>` and personal folders under `<data>/personal/<title>`, with safe lowercase names and numeric suffixes for collisions. Names with no usable characters fall back to the id. Projects with the same name share the project folder; their worktree names are kept distinct. Existing paths stay unchanged. Project checkout environments are unmanaged. Git worktrees and personal environments are managed; the environment record carries its provider. A personal folder is never retired by archive or the grace; only `ThreadOp::Delete` removes it, after a person approves a question that names the folder and its contents, and only when no other thread, project or environment is in or on it. The check and the deletion are one commit (the folder is marked `destroyed` in it), and `Run` and project add refuse a folder that is being removed. Startup finishes a removal a restart interrupted. A managed environment that a restart finds half made, with no thread on it, is destroyed and its folder removed by the first sweep. Archive stops a thread after 10 seconds, including its lifecycle dependents. Deleting a thread from the socket waits for a person: the calling thread (`KG_THREAD_ID`) gets a pending interaction, and with no thread `Workspace::ask_for_person` shows a standalone question. A click in the window uses that standalone question. Declining deletes nothing. Archive, unarchive and stop do not ask, and the archive dialog stays a window preference. A managed worktree retires 10 seconds after it has no unarchived threads; reuse and unarchive clear retirement. The grace deadlines persist, and GPUI timers check them after restart. Retiring a managed worktree removes its folder; its git branch stays so Restore can attach it again. The open right sidebar re-reads the changed-file list every two seconds. `kg environment changes`, `pull-request` and `open` were removed as unused (decision 36). Parentage does not control lifetime. The first sweep after startup removes again, the same way, each destroyed managed environment whose folder is still there because a restart interrupted its removal; a refused removal becomes `error`.

`kg mcp --thread <id>` is still the per-thread MCP bridge for plugin tools.

Core stores the validated `ThemeSettings` id and mode. UI owns theme files, colors and live reload.

The Browser tab shows one web page on macOS (decisions 117 and 118). `openUrl` still opens the system browser. A `downloads` key or `powers.spawn` is refused; no plugin used them, and `process.run` stays (decision 65). `plugins` serves thread Tools, CallTool and plugin operations through `Workspace::set_plugin_host`, a plain function, so core never depends on it. Without it, Tools returns an empty list, CallTool returns not-found and plugin operations return unavailable. Plugin install, update, reload and remove, and thread delete carry the calling thread (`KG_THREAD_ID`); approval is a pending interaction on that thread. Only the person in the app can answer it through `Workspace::answer`, a non-Op core method; a plugin cannot approve its own install or a thread deletion. Archive, unarchive and stop do not ask. `kg plugin dev` uses the same Reload approval. Without a calling thread, `Workspace::ask_for_person` exposes an in-memory approval to native UI; `Workspace::answer_standalone` answers through the same serialized request loop. Restart cancels standalone requests. A person-only question raised by a socket command goes when that command stops, and its op fails without acting (decision 93). Neither answer method is an Op or a plugin export. A pending interaction in the thread shows its options. Every answer is an `answered` event on the thread: the option id and the interaction's title. A permission question shows Decline and Approve. Delete and Remove show Cancel and that verb, and the window focuses Cancel. Synthetic `kg ui` input still cannot answer. Installed plugins and the powers a person approved are core records.

The native window is an `Op` (`Ui`). UI registers `Workspace::set_ui_driver` in `kg_ui::init`. Snapshot, click, type, key, scroll and screenshot run on the main thread through `Window::dispatch_event` (not OS events). Click and scroll first bring a clipped target into view by sending wheel events at a visible recorded ancestor. Synthetic dispatch sets a marker that person-only answer handlers ignore. Screenshot uses platform capture without focusing the window.

A thread environment's diff is an `Op` (`Diff`): the changed files, one file, and the commits that can be reviewed. Scopes are uncommitted, the branch against a base, and one commit. Diffs run off the UI thread and are cached per scope. A missing git and a missing base are errors. The view never edits the worktree. `file.changed` and `file.read` have no producer and no reader in the window; they stay in the event type list so old logs load. The review page reads one file's diff through `DiffOp::Show`. Nothing is marked as changed by an agent (decision 60).

Pending questions are answered through `Workspace::answer`. A plugin cannot answer an install, a thread delete, or a standalone approval, and synthetic `kg ui` cannot answer. Archive, unarchive and stop do not ask. `kg plugin dev` uses the same Reload approval. Without a calling thread, `Workspace::ask_for_person` exposes an in-memory approval to native UI; `Workspace::answer_standalone` answers through the same serialized request loop. Restart cancels standalone requests. A person-only question raised by a socket command goes when that command stops, and its op fails without acting (decision 93). Neither answer method is an Op or a plugin export. A pending interaction in the thread shows its options. Every answer is an `answered` event on the thread: the option id and the interaction's title. A permission question shows Decline and Approve. Delete and Remove show Cancel and that verb, and the window focuses Cancel.
